# План P6+: веб-дашборд диспетчера и владельца

## Цель
Создать отдельный веб-интерфейс `apps/dashboard`, который показывает оперативную и историческую статистику компании.

Это **не замена Django Admin**.

- **Django Admin** — редактирование данных, исправления, создание клиентов/товаров/заказов, детальный аудит.
- **Dashboard** — быстро посмотреть бизнес-состояние: продажи, заказы, курьеры, смены, склад, финансы.
- **Telegram-бот админа** — короткие сводки и быстрые уведомления.
- **Полный Admin Mini App** пока не делать: он будет дублировать Dashboard и потребует отдельной разработки React-интерфейса.

# 3. Страница «Главная»

Адрес:

```
/dashboard/
```

## 3.1. Общий фильтр периода

Вверху страницы должен быть фильтр:

```
[ Сегодня ] [ Вчера ] [ Неделя ] [ Месяц ] [ Всё время ]
Дата от: [____]  Дата до: [____] [ Применить ]
```

Правила:

- по умолчанию показывать **сегодня**;
- кнопка «Сегодня» — текущий день в часовом поясе `Asia/Samarkand`;
- «Неделя» — текущая календарная неделя;
- «Месяц» — текущий календарный месяц;
- «Всё время» — без ограничения периода;
- ручной диапазон должен быть включительным;
- если дата «от» больше даты «до» — показать понятную ошибку, не делать некорректный запрос.

Важно: один и тот же выбранный период должен применяться ко всем блокам страницы.

---

## 3.2. Верхние карточки KPI

Первая строка — финансы:

|Карточка|Источник|Пояснение|
|---|---|---|
|Доход|`Finance.income`|Все доходные операции за период|
|Расход|`Finance.consumption`|Все расходные операции|
|Прибыль|`Finance.profit`|Доход минус расход|
|Безнал|`Finance.card_profit`|Только входящие безналичные оплаты|
|Наличные по доставкам|Доставленные `Order` с оплатой наличными|Оперативная сверка доставок|

Вторая строка — заказы:

|Карточка|Источник|
|---|---|
|Создано заказов|`Order.created_at` за период|
|Доставлено|`Order.status = DELIVERED`, по `delivered_at`|
|В ожидании|Текущие `Order.status = PENDING`|
|Отменено|`Order.status = CANCELLED`, по дате изменения/создания — агент должен определить доступную корректную дату|
|Продано единиц|Сумма `OrderItem.quantity` у доставленных заказов|

Важно явно подписывать разницу:

```
Создано за период
Доставлено за период
```

Заказ может быть создан в один день, а доставлен в другой. Это разные показатели.

## 3.3. Активная работа прямо сейчас

Блок «Сейчас в работе»:

|Показатель|Что показывать|
|---|---|
|Активных смен|Количество `CourierShift` со статусом `OPEN`|
|Активных рейсов|Количество `CourierTrip` со статусом `ACTIVE`|
|Заказов в ожидании|Текущие `PENDING` заказы|
|Неназначенных заказов|`trip IS NULL` и/или без `assigned_courier` — по фактической логике проекта|
|Критических остатков|Количество складских позиций ниже порога|

Ниже — таблица активных смен:

|Курьер|Открыта|Текущий рейс|Заказов доставлено сегодня|Наличные|Карта|Действие|
|---|---|---|---|---|---|---|
|Ахмедов|08:15|Рейс №2|17|340 000|120 000|Открыть|

Кнопка «Открыть» ведёт на детальную страницу смены/рейса или в Django Admin.

## 3.4. Последние заказы

Таблица последних примерно 10–20 заказов:

|Номер|Создан|Клиент|Адрес|Курьер|Рейс|Сумма|Оплата|Статус|
|---|---|---|---|---|---|---|---|---|

Требования:

- использовать новый декоративный номер заказа, когда он появится;
- если у старого заказа номер отсутствует — корректно показывать `—` или технический ID;
- клик по строке ведёт на страницу деталей Dashboard либо на карточку заказа в Admin;
- статус отображать цветным badge:
    - `PENDING` — жёлтый;
    - `DELIVERED` — зелёный;
    - `CANCELLED` — красный.

# 5. Страница «Товары и тара»

Адрес:

```
/dashboard/products/
```

Это один из самых важных разделов для вашей компании.

## 5.1. Продажи по товарам

Таблица:

|Товар|Категория|Продано, шт.|Заказов с товаром|Выручка|Средняя цена|
|---|---|---|---|---|---|

Правила:

- учитывать только позиции доставленных заказов;
- количество — сумма `OrderItem.quantity`;
- количество заказов — число уникальных доставленных заказов, в которых есть данный товар;
- выручка — сумма финальной цены позиций `OrderItem.price`;
- сортировка по количеству продаж или выручке;
- должна быть возможность отфильтровать по типу товара.

Категории брать из существующих типов `Product`:

```
Вода
Вода 20 л с тарой
Тара
Кулеры
Аксессуары
```

## 5.2. Отдельный блок «Учёт тары»

Показывать только для позиций, где товар относится к воде с тарой (`BOTTLE_20L`) согласно реальной модели проекта.

|Показатель|Значение|
|---|---|
|Продано воды 20 л|Сумма `OrderItem.quantity`|
|Принято по обмену|Сумма `exchange_qty`|
|Продано с новой тарой|Сумма `sell_with_qty`|
|Принято брака|Сумма `defective_qty`|

Учитывать только доставленные заказы.

Важно:

- не смешивать «продано воды» и «списано тары»;
- складской остаток не вычислять по этим цифрам;
- остаток брать только из `StockBalance`;
- историю движений брать из `StockMovement`.

## 5.3. График продаж по дням — второй этап

Не обязателен для первого релиза, но планируется:

```
Продано воды 20 л по дням
Выручка по дням
```

На первом этапе можно реализовать таблицу без графиков. После проверки корректности данных добавить Chart.js.

# 9. Архитектурные требования

## 9.1. Не дублировать статистику в полях моделей

На первом этапе **не добавлять** в `Product`, `Worker`, `Order` поля вида:

```
total_sold
total_revenue
orders_count
delivered_orders_count
courier_income
```

Причина: это производные значения, которые легко становятся неверными при:

- отмене заказа;
- исправлении `OrderItem`;
- изменении цены;
- удалении или восстановлении данных;
- повторном срабатывании сигналов;
- исправлении доставки задним числом.

Статистика должна строиться из фактических данных:

```
Order
OrderItem
CourierShift
CourierTrip
StockBalance
StockMovement
Finance
FinancialTransactions
```

## 9.2. Сервисы статистики

Всю ORM-логику и агрегации вынести из views в сервисный слой.

Рекомендуемая структура:

```
apps/
├── dashboard/
│   ├── services/
│   │   ├── __init__.py
│   │   ├── filters.py
│   │   ├── overview.py
│   │   ├── orders.py
│   │   ├── products.py
│   │   ├── couriers.py
│   │   ├── stock.py
│   │   └── finance.py
│   ├── views.py
│   ├── urls.py
│   ├── templates/dashboard/
│   └── tests/
```

Допустимо расположить сервисы в `logistics` и `accounting`, если агент считает это лучше для существующей структуры. Главное правило:

> Представления получают параметры, вызывают сервис и передают подготовленный результат в шаблон.  
> Больших ORM-запросов и бизнес-расчётов в `views.py` быть не должно.

## 9.3. Единый объект фильтра периода

Нужен общий механизм разбора дат и выбора периода, чтобы на всех страницах одинаково работали:

```
today
yesterday
week
month
all
date_from
date_to
```

Не копировать один и тот же код проверки дат в каждую view.

## 9.4. Производительность запросов

Обязательные требования:

- использовать `select_related()` для одиночных FK;
- использовать `prefetch_related()` для `Order.items`, рейсов и заказов;
- не допускать N+1 запросов в таблицах;
- таблицы заказов и транзакций делать с пагинацией;
- не загружать всю историю заказов на одну страницу;
- агрегаты выполнять на уровне PostgreSQL через ORM;
- не считать статистику в Python-цикле по всем заказам.

## 9.5. Индексы

Агент должен изучить текущие модели и проверить, что существуют индексы для часто используемых выборок.

Ожидаемые кандидаты:

```
Order:
- status + delivered_at
- created_at
- trip + status
- assigned_courier + status, если это поле используется в отчётах

CourierShift:
- status + date
- courier + date

Finance:
- date

FinancialTransactions:
- date + type
```

Не добавлять индексы механически: сначала проверить текущие поля, `Meta.indexes`, реальные названия choices и существующие миграции.

# 10. Авторизация и доступ

Dashboard не должен быть публичным.

## Первый этап

Минимум:

- все `/dashboard/` доступны только авторизованным Django-пользователям;
- неавторизованного пользователя перенаправлять на стандартную страницу входа Django Admin или отдельный login;
- доступ разрешён:
    - `is_staff=True`;
    - или пользователям с отдельным разрешением/dashboard-группой.

## Рекомендуемый вариант

Создать группы Django:

```
Owner
Dispatcher
Warehouse manager
Accountant
```

Первый релиз может использовать только:

```
Owner / Dispatcher
```

Права:

|Раздел|Owner|Dispatcher|Warehouse|Accountant|
|---|---|---|---|---|
|Главная|✅|✅|при необходимости|при необходимости|
|Заказы|✅|✅|❌|❌|
|Курьеры|✅|✅|❌|❌|
|Склад|✅|просмотр|✅|❌|
|Финансы|✅|ограниченно/нет|❌|✅|

Если роли пока не готовы, начать с `is_staff`, но архитектурно не закрывать возможность перейти на группы.

# 11. UI и дизайн

## Технология первого этапа

Использовать уже предусмотренный подход:

```
Django Templates + Bootstrap 5 CDN + Bootstrap Icons
```

Не использовать React для Dashboard на первом этапе.

Причины:

- быстрее сделать;
- проще поддерживать;
- все данные уже в Django;
- не нужно создавать второй отдельный фронтенд;
- нет необходимости в сложной интерактивности на старте.

## Стиль

```
Слева — боковое меню.
Сверху — тёмная панель с названием проекта, пользователем и кнопкой выхода.
Основная область — таблицы и карточки.
```

Цвета статусов:

|Статус|Цвет|
|---|---|
|Доставлен|Зелёный|
|В ожидании|Жёлтый|
|Отменён|Красный|
|Смена открыта|Зелёный|
|Смена закрыта|Серый|
|Критический склад|Красный|

Требования:

- нормальная работа на ноутбуке и телефоне;
- таблицы на маленьком экране должны иметь горизонтальную прокрутку или адаптивное представление;

# Главное решение

Рекомендованная схема:

```
Фактические данные
Order / OrderItem / Shift / Trip / Stock / Finance
        ↓
Сервисный слой статистики
        ↓
Dashboard Templates
        ↓
Короткие команды Telegram-бота
```

То есть Dashboard и Telegram-бот не должны считать данные по-разному. Оба должны использовать один общий слой статистики. Это предотвратит ситуацию, когда в боте одна сумма, а на веб-странице другая.
