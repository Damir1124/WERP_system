# Скрытая команда курьера «/сводка» — агрегация заказов по адресу общежития

**Создан:** 2026-08-21
**Статус:** Реализовано
**Цель:** Дать курьеру возможность одним вводом команды увидеть, сколько воды нужно
в каждый блок/этаж/комнату общежития по его взятым заказам — без ручного
«собирания в голове» десятка разрозненных заказов.

---

## Зачем это нужно

Курьер берёт из пула десятки заказов, адреса которых выглядят как
«Блок A, 3 этаж, комната 12», «Блок B, 5 этаж, комната 7» и т.д. В голове собрать
«сколько воды в блок A на 3 этаж» — трудно и ошибочно. Особенно когда заказов
много и адреса почти однотипные, но не одинаковые.

**Почему именно скрытая команда, а не кнопка:**
- Команда не должна засорять меню — это служебный инструмент, а не ежедневное действие.
- Доступность только курьеру гарантируется **фильтром роли** в `tg_bot/bot.py`
  (`role == 'courier'`), а не видимостью кнопки. Даже если курьер знает команду,
  оператор/владелец/клиент её вызвать не смогут — их роутеры не обрабатывают `/сводка`.

---

## Стандарт ввода адреса общежития

Чтобы парсер мог разобрать адрес, вводим **единый формат**:

```
Блок A, 3 этаж, комната 12
```

| Поле | Обязательность | Формат |
|------|----------------|--------|
| **Блок** | обязательно | латинская буква A–Z или цифра |
| **Этаж** | обязательно | целое число |
| **Комната** | для агрегации не обязательна | целое число |

Допустимые синонимы: «блок/корпус/подъезд», «этаж/эт.», «комната/комн./кв./№».
Разделители любые (запятая, пробел, точка, дефис).

Примеры корректного ввода:
```
Блок A, 3 этаж, комната 12
Блок B 5 эт. комн. 7
Корпус 2, 4 этаж, кв 15
A 3 12
```

> 💡 **Почему парсер, а не структурированные поля:** адрес уже хранится как
> свободный текст в `Order.delivery_address_text` (снимок) и `ClientAddress.address_text`.
> Вводить структурированные поля (блок/этаж/комната) — это миграции + правки всех форм
> (оператор, курьер, клиент). Парсер по регуляркам решает задачу **сейчас**, без
> изменения схемы БД. Это осознанный компромисс: быстро, но хрупко к нестандартному вводу.

## Архитектура потока

```
/сводка (или /agg)
   │
   ▼  GET /api/bot/courier/orders/aggregate/
   │
   ▼  CourierOrdersAggregateView (apps/bot_bridge/views.py)
   │     • находит активный рейс курьера (CourierShift OPEN → CourierTrip ACTIVE)
   │     • берёт PENDING-заказы этого рейса
   │     • сериализует через OrderSerializer
   │
   ▼  aggregate_orders_by_address() (apps/logistics/services.py)
   │     • для каждого заказа парсит delivery_address_text
   │     • группирует по (блок, этаж)
   │     • суммирует воду 19л по этажу + детализация по комнатам
   │
   ▼
   📦 Сводка по адресам
   🏢 Блок A
      3 этаж — 4 шт
         комната 12 — 3 шт
         комната 15 — 1 шт
   🏢 Блок B
      5 этаж — 3 шт
         комната 7 — 3 шт
```

Заказы с нераспознанным адресом (нет блока или этажа) попадают в `unparsed` и
выводятся **отдельными inline-кнопками** — курьер может открыть каждый и посмотреть
адрес вручную. Так ничего не теряется.

## Реализация

### 1. Парсер — `apps/logistics/services.py`
`parse_dormitory_address(text) -> dict | None` извлекает `block`, `floor`, `room`
по регуляркам. Если поле не распознано — `None`.

**Почему регулярки, а не split по запятым:** адрес может быть введён без запятых
(«Блок B 5 эт. комн. 7») или с разными синонимами. Регулярки устойчивее к вариациям.

### 2. Агрегация — `apps/logistics/services.py`
`aggregate_orders_by_address(orders) -> dict`:
- группирует по `(block, floor)`;
- `water_qty` — сумма воды 19л (тип `19W`) на этаж;
- `rooms` — список `{room, water_qty}` для детализации по комнатам;
- `unparsed` — заказы без блока/этажа.

**Почему двухуровневая (этаж + комнаты):** курьеру важно видеть и общий объём на
этаж (сколько всего поднять), и разбивку по комнатам (куда именно заносить).

### 3. API — `apps/bot_bridge/views.py`
`CourierOrdersAggregateView` (`GET /courier/orders/aggregate/`), permission `IsCourier`.
Берёт заказы курьера в активном рейсе, сериализует, вызывает агрегацию.

### 4. Команда — `tg_bot/routers/courier.py`
Обработчик `Command("сводка")` / `Command("agg")`. Формирует сообщение-список.
Доступность только курьеру — через фильтр роли в `bot.py`.

### 5. Тесты — `tests/logistics/test_dormitory_aggregation.py`
10 тестов: парсер (разные форматы) + агрегация (группировка, комнаты, unparsed, сортировка).

### 6. Тестовые данные — `apps/logistics/management/commands/seed_dormitory_orders.py`
Команда `python manage.py seed_dormitory_orders` создаёт 10 заказов в пуле
с адресами общежития (включая 2 «неагрегируемых» для проверки кнопок).

## Связи с другими модулями
- `apps/logistics/` — модели `Order`, `OrderItem`, `CourierShift`, `CourierTrip`; сервисы парсинга/агрегации.
- `apps/bot_bridge/` — API-эндпоинт, сериализаторы, URL.
- `tg_bot/` — роутер курьера, фильтр роли в `bot.py`.
- `apps/products/` — тип продукта `19W` (вода) для подсчёта количества.

## ⚠️ Известные ограничения
- Парсер хрупок к нестандартному вводу адреса (например, «общежитие, 3 этаж, без
  номера комнаты»). Такие заказы не теряются — попадают в `unparsed` и выводятся кнопками.
- Если адрес введён без блока или этажа — заказ не агрегируется.
- Команда работает только по заказам **активного рейса** курьера (PENDING).
