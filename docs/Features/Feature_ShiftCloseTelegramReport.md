# Фича: Автоотчёт о закрытии рейса/смены в Telegram админ-чат

> Дата: 2026-08-19
> Модуль: `apps/bot_bridge/`
> Статус: реализовано, 9 тестов + 60 тестов bot_bridge/dashboard OK

## Зачем это нужно

Когда курьер закрывает рейс или смену в мини-приложении, владелец/диспетчер должен
**мгновенно** видеть итоги: сколько денег собрано, сколько воды продано и сколько тары
осталось в машине. Раньше эти данные были доступны только в дашборде — нужно было
заходить и выбирать дату. Теперь отчёт сам приходит в Telegram админ-чат в момент
закрытия.

Ключевое требование: **отправка должна срабатывать автоматически и надёжно, даже если
приложение курьера свёрнуто**. Поэтому триггер живёт на сервере, а не во фронтенде.

## Почему триггер на сервере, а не во фронтенде

Фронтенд (`TripClose.jsx` / `ShiftClose.jsx`) лишь вызывает `POST .../close/`. Если бы
отчёт отправлял фронтенд, он бы зависел от состояния приложения: свёрнутое приложение,
обрыв сети, закрытие вкладки — и отчёт потерялся бы.

Серверный подход:
- закрытие рейса/смены — это **единственная точка** в `TripCloseView.post()` и
  `CourierShiftCloseView.post()`;
- после успешного `save()` сервер сам формирует и отправляет отчёт;
- данные берутся из БД (источник истины), а не из `location.state` фронтенда —
  значит, отчёт всегда точен, даже если курьер менял количество через бот.

## Почему «вычисляем на лету», а не храним снимок

Тот же принцип, что в `Feature_ShiftReports`: отчёт строится из существующих моделей
(`CourierShift` → `CourierTrip` → `Order` → `OrderItem`) в момент закрытия. Снимок
не нужен — данные уже зафиксированы статусом `CLOSED`/`DONE`, а пересчёт занимает
миллисекунды.

## Единый расчёт с mini-app курьера (без расхождений)

Чтобы цифры в Telegram совпадали с тем, что курьер видел на экране, используются
**те же методы**, что питают `Trip.jsx`:

| Метрика | Источник | Где ещё используется |
|---------|----------|----------------------|
| Взято / пустых / остаток | `CourierTrip.get_trip_summary()` | `CourierCurrentTripView` → `Trip.jsx` |
| Наличные / карта по рейсу | агрегация `OrderItem` по `payment_type` | `CourierCurrentTripView`, `dashboard/reports.py` |
| Сводка смены (вода, рейсы, деньги) | `get_shift_report()` из `dashboard/services/reports.py` | дашборд «Отчёты» |
| Номер авто | `Garage` (OneToOne к курьеру) | админка автопарка |

> 💡 **Почему так:** если бы отчёт считал деньги из кэшированных полей
> `CourierShift.cash_total/card_total`, он мог бы показать устаревшие цифры — сигнал
> пересчёта обновляет БД через `queryset.update()`, не затрагивая объект в памяти.
> Прямой подсчёт из `OrderItem` всегда точен.

## Структура сообщения (HTML)

**Рейс:**
```
🏁 <b>Рейс закрыт</b>

🕐 Время закрытия: 19.08.2026 20:45
🚚 Рейс: #12
👤 Курьер: Иван Иванов
🚗 Авто: 123ABC (Газель)

💰 <b>Финансы</b>
• Наличные: 120 000 сум
• Карта: 80 000 сум
• Итого: 200 000 сум
• Продано воды: 10 бак

📦 <b>Тара</b>
• Взято: 50 бак
• Возвращено пустых: 8 шт
• Осталось в машине: 40 бак
```

**Смена** — аналогично, но тара агрегируется по всем рейсам смены, добавляются
«Заказов выполнено» и «Рейсов».

## Ключевые решения в коде

### 1. Новый модуль `apps/bot_bridge/reports.py`

Изолирует построение текста и отправку от существующих вьюх:

- `build_trip_report_text(trip)` / `build_shift_report_text(shift)` — чистые функции,
  возвращают HTML-строку (легко тестировать без сети);
- `notify_trip_closed(trip)` / `notify_shift_closed(shift)` — резолвят получателей и
  вызывают `send_telegram_message()` из `notify.py`;
- `_resolve_admin_chat_ids()` — список получателей: **все** сотрудники с
  `worker_type=OWNER` и `tg_id` + `settings.ADMIN_CHAT_ID` (если задан), дедупликация.

### 2. Отчёт уходит всем владельцам

По ТЗ отчёт должен получать **каждый** владелец (`worker_type=OWNER` с `tg_id`), а не
один админ. Поэтому `_resolve_admin_chat_ids()` собирает всех владельцев из БД.
`ADMIN_CHAT_ID` в `settings.py` (из `.env`) — **дополнительный** получатель, удобен
для отправки в группу (отрицательный chat_id). Список дедуплицируется, чтобы не
слать дубликаты, если `ADMIN_CHAT_ID` совпадает с tg_id владельца.

### 3. Тара по смене — сумма по рейсам

У смены может быть несколько рейсов, поэтому «Взято/Пустых/Осталось» суммируются по
всем рейсам через `get_trip_summary()` — тот же метод, что в mini-app.

### 4. Отправка не блокирует ответ API

`send_telegram_message()` использует `requests` с `timeout=10` и возвращает `False`
при ошибке, не бросая исключение. Закрытие рейса/смены не «падает» из-за проблем с
Telegram — отчёт лишь логируется как неудачный.

### 5. Ленивый импорт `notify.py`

`notify.py` требует `requests`, которого может не быть в весте. Чтобы приложение
стартовало без него, `reports.py` импортирует `send_telegram_message` **внутри**
функции `_send_to_admins()` с `try/except` — тот же паттерн, что в views.py:644.
Если `requests` отсутствует, отчёты не отправляются (логируется предупреждение),
но эндпоинты закрытия продолжают работать. Отправка идёт каждому получателю
отдельно; `True` возвращается, если хотя бы одно сообщение ушло успешно.

> Требование: для реальной отправки отчётов в venv должен быть установлен `requests`
> (он объявлен в `requirements_bot.txt`, но отсутствует в `requirements.txt`).

## Edge cases (покрыты тестами)

- Рейс без заказов → нули в финансах и таре, отчёт всё равно уходит.
- Авто не привязано к курьеру → строка «Авто» отсутствует.
- Несколько владельцев → отчёт уходит каждому.
- `ADMIN_CHAT_ID` добавляется к списку владельцев (дедупликация).
- Получателей нет вовсе (нет владельцев и `ADMIN_CHAT_ID`) → `False` без исключения.
- Несколько рейсов в смене → тара суммируется корректно.

## Производительность

Для типичной смены (несколько рейсов × несколько заказов) — несколько агрегатных
запросов `SUM` по `OrderItem` + `get_trip_summary()` на рейс. Это миллисекунды,
кэшировать нечего.
