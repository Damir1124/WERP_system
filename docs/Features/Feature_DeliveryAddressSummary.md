# Feature: Визуальное усиление блока «Адрес доставки» в клиентском Mini App

> Дата реализации: 2026-08-31
> Статус: ✅ Завершено (v2: убран дубль, три состояния, компактный блок)
> Область: `frontend/client` (клиентское мини-приложение)

## Зачем это нужно

Раньше адрес доставки был **рядовым текстовым полем формы** — визуально равноценным «Примечанию» или «Телефону». Клиент, который проверяет «куда едет заказ», должен был искать адрес среди прочих полей. Данные были разбросаны по `address`, `latitude/longitude`, `selectedAddressId`, `savedAddresses` — и каждый экран определял «что показывать» своей собственной логикой.

**Цель:** дать клиенту однозначный, заметный, не пропускаемый визуально ответ на вопрос «куда привезут заказ» на каждом шаге: в корзине, при оформлении/редактировании и в списке заказов.

## Ключевое архитектурное решение: единый резолвер

### Проблема дублирования логики

До рефакторинга в `Cart.jsx` была своя логика определения адреса (строки 97-110 `handleCheckout`), в `OrderForm.jsx` — своя (выбор сохранённого адреса сразу вписывал текст в поле), в `OrderEdit.jsx` — третья. Любое изменение правил «какой адрес реально уйдёт в заказ» требовало правки трёх мест.

### Решение: `resolveDeliveryAddress()`

**Файл:** `frontend/client/src/utils/address.js`

```javascript
export function resolveDeliveryAddress({ address, latitude, longitude, selectedAddressId, savedAddresses = [] }) {
  // 1. Приоритет: выбранный сохранённый адрес (selectedAddressId)
  // 2. Затем: текстовый адрес (address)
  // 3. Затем: только координаты (latitude/longitude)
  // 4. Иначе: isEmpty = true
}
```

**Почему именно такой порядок приоритетов:**
1. **Сохранённый адрес** — самый «богатый» источник: у него есть и текст, и координаты, и лейбл («Дом», «Офис»). Если клиент выбрал его кнопкой — это его явное намерение.
2. **Текстовый адрес** — клиент ввёл вручную. Координаты могут быть, а могут отсутствовать.
3. **Только координаты** — клиент указал точку на карте без текста.

### Нормализация координат через `Number()`

**Почему это важно:** из API координаты могут прийти строками (`"39.6542"`), а `toFixed()` работает только с числами — `"39.6542".toFixed(5)` упадёт с `TypeError`. Функция `toNumber()` внутри резолвера приводит строки к числам и отбрасывает `NaN`/`null`/пустые строки.

```javascript
function toNumber(value) {
  if (value == null || value === '') return null
  const n = Number(value)
  return Number.isFinite(n) ? n : null
}
```

## Компонент-резюме: `DeliveryAddressSummary`

**Файл:** `frontend/client/src/components/DeliveryAddressSummary.jsx`

### Три состояния

| Состояние | Визуал | Смысл |
|-----------|--------|-------|
| **Адрес не указан** (`isEmpty`, без ошибки) | Нейтральная серая строка + **подсвеченная подсказка** «Нажмите, чтобы указать, куда привезти заказ» | Спокойное напоминание + явный призыв к действию |
| **Укажите адрес** (`isEmpty` + `highlightError`) | Красная рамка + анимация `shake-once` | После нажатия «Оформить» без адреса: «Укажите адрес» |
| **Адрес указан** | Компактная синяя градиентная карточка | «Куда привезём заказ» + текст адреса |

**Почему три состояния вместо двух:** пользователь не должен видеть тревожный красный акцент постоянно — только в момент, когда он реально пытается оформить без адреса. В спокойном состоянии блок нейтральный и не давит на глаза.

**Подсказка в пустом состоянии:** под «Адрес не указан» выводится вторая строка с ключом `address_not_selected_hint` («Нажмите, чтобы указать, куда привезти заказ»), подсвеченная синим (`text-blue-500 font-semibold`) — клиент сразу понимает, что блок кликабельный и что от него требуется.

### Подсветка блока ввода при «Изменить»

Когда адрес уже указан и клиент нажимает «Изменить», блок ввода адреса подсвечивается на ~1.5 сек: синяя рамка + мягкая пульсация (`address-editor-highlight` в `index.css`). Это помогает глазу мгновенно найти поле, куда нужно вносить правки, особенно когда редактор раскрывается/скроллится из другого места экрана (например, из sticky-футера корзины).

```css
@keyframes addressPulse {
  0%, 100% { box-shadow: 0 0 0 0 rgba(37, 99, 235, 0.35); }
  50% { box-shadow: 0 0 0 6px rgba(37, 99, 235, 0.12); }
}
.address-editor-highlight {
  border-color: #3b82f6 !important;
  animation: addressPulse 0.8s ease-in-out 2;
}
```

Реализовано через state `editorHighlight` в каждом экране: `onEdit` → `setEditorHighlight(true)` + сброс через 1500 мс; класс применяется к блоку `#delivery-address-editor`.

### Проп `anchorId` — почему он нужен

В `Cart.jsx` и `OrderEdit.jsx` компонент рендерится **дважды**: в верхней части экрана и в sticky-футере. Если оба экземпляра будут иметь `id="delivery-address-anchor"` — `document.getElementById()` вернёт первый попавшийся, и `scrollIntoView` поведёт пользователя не туда. Поэтому `anchorId` — параметризуемый проп с дефолтом `'delivery-address-anchor'`, а футерные экземпляры получают `anchorId="delivery-address-anchor-footer"`.

### Проп `lang` — мультиязычность

Проект мультиязычный (RU/UZ/EN). Вместо захардкоженных строк из ТЗ компонент использует `t('address_not_selected', lang)` и т.д. — 5 новых ключей добавлены в `i18n.js` во все 3 языка.

## Валидация: scroll + shake вместо «немого» setError

**Паттерн во всех трёх формах** (`Cart.jsx`, `OrderForm.jsx`, `OrderEdit.jsx`):

```javascript
const resolved = resolveDeliveryAddress({ address, latitude, longitude, selectedAddressId, savedAddresses })
if (resolved.isEmpty) {
  setAddrError(true)
  document.getElementById('delivery-address-anchor')?.scrollIntoView({ behavior: 'smooth', block: 'center' })
  setTimeout(() => setAddrError(false), 1500)
  return
}
```

**Почему это лучше старого `setError(t('address_required'))`:**
- Старый вариант показывал текст ошибки **вверху экрана**, а поле адреса могло быть внизу — пользователь не понимал, что от него хотят.
- Новый вариант **физически скроллит** к блоку адреса и подсвечивает его красной рамкой с анимацией «тряски» (`shake-once` в `index.css`).

**CSS анимация** (`frontend/client/src/index.css`):

```css
@keyframes shakeOnce {
  0%, 100% { transform: translateX(0); }
  20% { transform: translateX(-4px); }
  40% { transform: translateX(4px); }
  60% { transform: translateX(-3px); }
  80% { transform: translateX(3px); }
}
.shake-once { animation: shakeOnce 0.4s ease; }
```

## Изменения по экранам

## Фикс карты в `LocationPicker` (чёрный экран)

**Симптом:** после нажатия «Указать на карте» открывался чёрный экран вместо карты.

**Причина:** тайлы OpenStreetMap (`tile.openstreetmap.org`) не загружаются внутри Telegram WebView (ограничения на внешние HTTP-запросы через ngrok), а фон контейнера карты в тёмной теме Telegram наследует `--tg-theme-bg-color` (чёрный). В итоге — чёрный прямоугольник вместо карты. Это не CSP на бэкенде (в `settings.py`/`docker-compose.yml` CSP-заголовков нет).

**Решение (в `frontend/client/src/components/LocationPicker.jsx`):**
1. **Явный светлый фон** контейнера карты (`bg-gray-100`) — вместо чёрного экрана теперь серый фон, даже если тайлы не загрузились.
2. **Кнопка «Отправить текущую локацию»** (`handleSendCurrentLocation`) — работает **без карты**: сразу запрашивает геолокацию через `navigator.geolocation`, вызывает `onLocationSelect(lat, lon)` и закрывает окно. Это надёжный путь, не зависящий от загрузки тайлов.

Новый i18n-ключ `send_current_location` («Отправить текущую локацию» / «Joriy joylashuvni yuborish» / «Send current location») добавлен во все 3 языка.

---

### `Cart.jsx` — корзина

1. **Единственный блок адреса — в sticky-футере** над кнопкой «Оформить заказ» (компактный). Верхний дубль убран — адрес виден ровно в момент принятия решения об оплате, без навязчивого повтора вверху.
2. **Раскрывающийся блок «Изменить адрес»** — сохранённые адреса + инпут + геолокация раскрываются по клику на блок адреса в футере (`showAddressEditor` state), с автоскроллом к редактору.
3. **`handleCheckout`** — использует единый резолвер + scroll+shake к футерному блоку.

### `OrderForm.jsx` — оформление заказа

1. **Добавлен `selectedAddressId`** (по образцу `Cart.jsx`) — раньше выбор сохранённого адреса сразу вписывал текст в поле, из-за чего **лейбл («Дом: ул. Ленина 5») терялся**. Теперь кнопка подсвечивается, поле остаётся пустым, а лейбл попадает в резюме через резолвер.
2. **Блок адреса поднят выше** — сразу после карточки товара, до количества и оплаты. Порядок восприятия: *что заказываю → куда доставить → как оплатить*. Это единственный блок адреса на экране (компактный дубль из «Итого» убран).

### `OrderEdit.jsx` — редактирование заказа

1. **Блок адреса поднят под заголовок** — до списка товаров-степперов.
2. **Резюме над инпутом** — карточка редактирования остаётся в потоке формы (тут нет модалки). Это единственный блок адреса на экране (компактный дубль из sticky-футера убран).

### `MyOrders.jsx` — список заказов

Адрес вынесен из общего потока текста (`text-sm text-gray-600`) в **отдельный чип**: светло-синий фон (`bg-blue-50`), иконка `ICONS.location`, заголовок-капс «АДРЕС», жирный текст. Размещён сразу под номером/статусом, до состава — курьерская доставка важнее состава для клиента, который проверяет «куда едет».

## Как не допустить ошибок

### ❌ Дублировать логику определения адреса в каждом экране

Каждый экран раньше имел свою версию «какой адрес уйдёт в заказ». Любое изменение правил — три правки.

**✅ Правильно:** единый `resolveDeliveryAddress()` в `utils/address.js`, используется одинаково во всех формах.

### ❌ Забыть про строковые координаты

`toFixed()` на строке падает. Координаты из API могут быть строками.

**✅ Правильно:** нормализация через `Number()` внутри резолвера.

### ❌ Дублировать `id="delivery-address-anchor"` при двух экземплярах компонента

`getElementById` вернёт первый попавшийся — scroll уведёт не туда.

**✅ Правильно:** параметризуемый проп `anchorId`.

### ❌ Захардкодить строки в компоненте

Проект мультиязычный. Строки должны жить в `i18n.js`.

**✅ Правильно:** компонент принимает `lang` и использует `t()`.
