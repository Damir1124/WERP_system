# Фича: Отчёты по сменам курьеров (Dashboard)

> Дата: 2026-08-19
> Модуль: `apps/dashboard/`
> Статус: реализовано, 12 тестов + 50 тестов dashboard OK

## Зачем это нужно

Диспетчеру и владельцу нужна **сводка по каждой смене курьера**: сколько воды продано,
сколько рейсов сделано, сколько наличных и карты собрано, и — главное — **детализация
до каждого заказа и позиции**. Раньше эти данные были разбросаны по разным страницам
(смены, заказы, финансы) и не собирались в единый отчёт.

Ключевое требование пользователя: **выбрать любую дату → увидеть отчёты по всем сменам
этого дня**. Поэтому отчёт сделан датовым, а не привязанным к одной смене.

## Почему «вычисляем на лету», а не храним снимок

Отчёт полностью выводится из существующих моделей
(`CourierShift` → `CourierTrip` → `Order` → `OrderItem`). Мы **не создаём** таблицы
`ShiftReport`/`TripReport`/`OrderReport` и **не делаем миграций**, потому что:

- **Нет дублирования данных.** Снимок отчёта устаревает, как только меняется заказ
  (например, курьер подтвердил доставку после закрытия смены). Вычисление на лету
  всегда показывает актуальную картину.
- **Нет риска рассинхрона.** Хранить копию «истины» — значит поддерживать её в актуальном
  состоянии сигналами. Это лишняя сложность и источник багов.
- **Объём мал.** Смена = несколько рейсов × несколько заказов. Полный пересчёт за дату
  занимает миллисекунды, поэтому кэшировать нечего.

> 💡 **Правило:** если данные можно вычислить из источника истины за O(1)–O(n) с малым n —
> вычисляй на лету. Снимок оправдан только когда пересчёт дорогой или нужна историческая
> фиксация «как было на момент закрытия».

## Структура отчёта

Иерархия **смена → рейсы → заказы → позиции**:

| Уровень | Что показывает | Источник |
|---------|----------------|----------|
| **Смена** | продано воды, рейсов, наличные, карта, итого | `CourierShift` + агрегация `OrderItem` |
| **Рейс** | взято воды, привезено пустых, остаток | [`get_trip_summary()`](../Modules/Modules_Logistics.md) |
| **Рейс** | наличные / карта по рейсу | агрегация `OrderItem` по `payment_type` |
| **Заказ** | номер, адрес, оплата, сумма | `Order` (`human_number`, `delivery_address_text`, `get_total_price()`) |
| **Позиция** | наименование, кол-во, сумма | `OrderItem` (`product.name`, `quantity`, `price`) |

## Ключевые решения в коде

### 1. Наличные/карта считаем напрямую из `OrderItem`, а не из полей смены

У `CourierShift` есть кэшированные поля `cash_total`/`card_total`, которые обновляет сигнал
[`update_shift_totals_on_order`](../Concepts/Concepts_DjangoSignals.md). Но мы в отчёте
считаем их **заново** через `_sum_delivered_price_for_shift()`:

```python
total = OrderItem.objects.filter(
    order__trip__shift=shift,
    order__status=Order.Status.DELIVERED,
    order__payment_type=payment_type,
).aggregate(total=Sum('price'))['total']
```

**Почему:** сигнал обновляет БД через `queryset.update()`, не затрагивая объект в памяти.
Если передать в отчёт объект смены, полученный до срабатывания сигнала, кэшированные поля
будут устаревшими. Прямой подсчёт из `OrderItem` — это источник истины, он всегда точен
и не зависит от порядка срабатывания сигналов.

### 2. Вода — только тип `WATER`

«Продано воды» считаем по `product__type_product=Product.TypeProduct.WATER` (это «Вода 19»).
Тип `BOTTLE_20L` («Вода + тара 19») намеренно не включён — по ТЗ нужна именно «Вода 19».
Добавить его — одна строка в фильтре.

### 3. BONUS не входит в наличные/карту

Считаем только `CASH` и `CARD` (как в сигнале пересчёта смены). Заказы с оплатой `BONUS`
учитываются в «продано воды», но не в денежных итогах.

### 4. Данные рейса — тот же формат, что в mini-app курьера

Используем [`get_trip_summary()`](../Modules/Modules_Logistics.md), который возвращает
`full_loaded`, `empty_received`, `full_remain`. Это гарантирует, что «остаток» в отчёте
совпадает с тем, что курьер видит в своём mini-app — единый источник расчёта тары.

## Edge cases (покрыты тестами)

- Смена без рейсов → `trips=[]`, `total_trips=0`.
- Рейс без заказов → `orders=[]`, наличные/карта = 0.
- Смешанные оплаты (CASH + CARD) → корректная разбивка по рейсу и смене.
- BONUS → не входит в наличные/карту, но вода учитывается.
- Некорректная дата в URL → страница рендерится с сообщением об ошибке, без падения.
- `get_reports_for_date()` фильтрует смены строго по дате.

## Производительность

Для заказов и позиций используются `select_related`/`prefetch_related` — нет N+1 по
заказам. Для типичной смены (несколько рейсов × несколько заказов) полный рендер
оптимален; пагинация не требуется. Если в будущем на одну дату будет приходиться
сотни смен — можно добавить пагинацию по сменам.
