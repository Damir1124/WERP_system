# Главный принцип Admin для WERP

Разделите сущности на 3 типа.

|Тип|Примеры|Как работать в Admin|
|---|---|---|
|Справочники|Клиенты, товары, сотрудники, автомобили|Полное создание и редактирование|
|Операционные данные|Заказы, смены, рейсы|Ограниченное редактирование, действия по правилам|
|Учётные документы / история|Транзакции, складские движения, финансы, кассовая сверка|В основном только просмотр|

Это важно, потому что в проекте есть сигналы:

```
Order DELIVERED
→ склад
→ финансы
→ итоги смены
```

Если дать админу возможность свободно менять доставленный заказ, цену или количество, можно испортить склад, деньги и отчёты.

# 1. Заказы — главный рабочий экран Admin

## Как должен выглядеть список заказов

В списке сразу должны быть видны:

|Поле|Зачем|
|---|---|
|Декоративный номер|Курьеру и диспетчеру удобно ориентироваться|
|Технический `id`|Надёжный поиск и разбор ошибок|
|Дата/время создания|Когда заказ поступил|
|Клиент|Кому доставка|
|Телефон|Быстро позвонить|
|Адрес доставки|Куда везти|
|Курьер|Кто выполняет|
|Смена / рейс|В какой логистике находится|
|Сумма|Сумма всего заказа|
|Оплата|Наличные / карта / бонус|
|Статус|Ожидает / доставлен / отменён|
|Время доставки|Когда доставили|

Пример строки:

```
ID 15482 | №042 | 10.08 09:14 | Алиев Бахром | +998... |
ул. Навои, 15 | Ахмедов | Рейс №2 | 40 000 | Наличные | Доставлен
```

## Фильтры

Обязательные фильтры:

```
Статус заказа
Дата создания
Дата доставки
Тип оплаты
Курьер
Смена
Рейс
Товар
```

Дополнительно полезно:

```
Есть рейс / без рейса
Есть назначенный курьер / не назначен
```

## Поиск

Поиск должен работать по:

```
Техническому ID заказа
Декоративному номеру
ФИО клиента
Телефону клиента
Адресу
Примечанию
```

Но короткий номер может повторяться после 999, поэтому при результатах поиска обязательно показывать:

```
ID + дата + клиент + статус
```

а не только `№042`.

---

## Карточка заказа

Карточку заказа сделать разделённой на понятные блоки:

```
1. Статус и номер
2. Клиент и адрес доставки
3. Логистика: курьер, смена, рейс
4. Оплата и сумма
5. Позиции заказа
6. Время создания / доставки / отмены
7. Служебная информация
```

### Блок «Статус и номер»

```
Технический ID — только чтение
Декоративный номер — только чтение
Статус
Дата создания — только чтение
Дата доставки — только чтение
```

### Блок «Клиент и адрес»

Важно показывать:

- текущего клиента;
- **адрес-снимок заказа**, а не только текущий адрес клиента;
- телефон клиента;
- геолокацию, если есть.

Для старых доставок нельзя автоматически менять исторический адрес, если клиент потом поменял адрес в CRM.

### Блок «Позиции заказа»

Использовать `OrderItem` как inline-таблицу:

|Товар|Количество|Цена позиции|Обмен тары|С тарой|Брак|
|---|---|---|---|---|---|

Поля:

```
Цена позиции — readonly после сохранения.
```

Если цена пересчитывается существующим signal, агент должен не сломать его.

---

## Правила редактирования заказа

Это критически важно.

### Пока заказ `PENDING`

Разрешить:

```
Менять клиента
Менять адрес-снимок
Менять позиции
Менять количество
Менять тип оплаты
Назначать курьера
Прикреплять к рейсу
Менять комментарий
Отменять заказ
```

### Когда заказ `DELIVERED`

По умолчанию запретить обычное редактирование:

```
Нельзя менять:
- позиции;
- количество;
- цену;
- тип оплаты;
- статус;
- рейс;
- курьера;
- дату доставки;
- адрес-снимок.
```

Потому что эти данные уже могли сформировать:

```
финансовую транзакцию;
движение склада;
итоги смены;
отчёт кассы;
статистику Dashboard.
```

Если надо исправить ошибку по доставленному заказу, правильный путь:

```
1. Создать отдельное действие «Исправление доставленного заказа».
2. Или отменить финансовую/складскую проводку контролируемо.
3. После этого изменить заказ.
4. Пересчитать затронутую смену, финансы и склад.
5. Сохранить аудит причины исправления.
```

Не давать обычному диспетчеру просто поменять цифры в доставленном заказе.

### Когда заказ `CANCELLED`

Разрешить редактировать только комментарий/причину отмены, если бизнес-логика это допускает.

---

## Admin-действия для заказов

Нужные массовые действия:

```
- Назначить в смену / рейс
- Назначить курьера
- Отменить выбранные pending-заказы
- Экспортировать выбранные заказы
- Открыть маршрут / список адресов
```

Не нужны массовые действия:

```
- «Отметить доставленным» без проверки
- «Удалить заказы»
- «Поменять оплату у доставленных»
```

Доставку лучше подтверждать через ваш существующий курьерский flow в Telegram / Mini App. Admin может иметь это действие только для владельца/старшего диспетчера и с подтверждением.

# 2. Смены и рейсы — не редактировать свободно

## Список смен

Показывать:

```
Курьер
Дата
Статус
Открыта
Закрыта
Наличные по системе
Карта по системе
Итого
Рейсов
Доставлено заказов
Статус сверки кассы
```

Фильтры:

```
Дата
Курьер
OPEN / CLOSED
Касса: ожидает / совпало / расхождение
```

На смене нужна большая кнопка-ссылка:

```
[ Открыть отчёт Dashboard ]
```

которая ведёт на:

```
/dashboard/shifts/<shift_id>/
```

Dashboard удобнее для проверки, Admin — для глубокой правки и аудита.

---

## Карточка смены

Сделать почти всё readonly:

```
Курьер
Дата
Время открытия
Время закрытия
Наличные по системе
Карта по системе
Статус
```

Внутри показать inline рейсы.

Для закрытой смены запретить редактирование логистических и денежных полей обычным пользователям.

Разрешённые действия:

```
- Закрыть смену — только если нет активного рейса;
- Открыть Dashboard-отчёт;
- Перейти к кассовой сверке;
- Скачать путевой лист / отчёт, если реализован;
- Экспортировать заказы смены.
```

## Рейсы внутри смены

В `CourierShiftAdmin` показывать inline рейсы:

```
Рейс №
Статус
Загружено полных
Возвращено полных
Начат
Завершён
Заказов
```

Но не пытаться в inline редактировать все заказы и складские показатели одновременно — это станет неудобно и опасно.

Для каждого рейса должна быть ссылка:

```
[ Открыть рейс ]
```

---

## Карточка рейса

Отображать:

```
Смена
Курьер
Номер рейса
Статус
Загружено полных
Возвращено полных
Начало
Завершение
```

Показатели, которые рассчитываются автоматически, сделать readonly:

```
Доставлено
Остаток полных
Пустые по обмену
Продано с тарой
Брак
Наличные
Карта
Итого
```

Заказы показать через readonly inline или ссылкой на список заказов с уже применённым фильтром рейса.

После завершения рейса не позволять менять:

```
full_loaded
full_returned
статус
заказы
```

без специального исправительного сценария.

# 3. Кассовая сверка смены

Если агент добавит отдельную модель кассовой сверки, её нужно сделать удобной в Admin.

## Список сверок

|Смена|Курьер|Дата|Ожидалось наличных|Принято|Разница|Статус|Принял|Время|
|---|---|---|---|---|---|---|---|---|

Статусы:

```
Ожидает сверки
Совпадает
Расхождение
```

Цветовая индикация:

```
Совпадает — зелёный
Ожидает — жёлтый
Расхождение — красный
```

## Карточка сверки

Поля только для чтения:

```
Смена
Курьер
Ожидаемые наличные
Разница
Статус
Кто принял
Когда принял
```

Редактируемые поля:

```
Фактически принято наличных
Комментарий
```

После сохранения:

- разница пересчитывается автоматически;
- статус меняется автоматически;
- фиксируется кто внёс запись и когда;
- повторное редактирование доступно только владельцу/кассиру с правом.

# 5. Товары

## Список товаров

|Наименование|Тип|Цена|Учёт на складе|Остаток|Продано в WERP|Статус|
|---|---|---|---|---|---|---|

Но здесь важно:

- остаток и продано — вычисляемые показатели;
- не позволять редактировать их прямо в таблице;
- редактировать можно только справочные свойства товара.

Редактируемые:

```
Название
Тип
Цена
Учитывать на складе
Минимальный остаток — если появится такое поле
Активен / неактивен — желательно добавить вместо удаления
```

### Не удалять товары, которые уже были в заказах

Если товар больше не продаётся:

```
active = False
```

или аналогичное поле.

Не удалять, потому что `OrderItem` и история должны остаться корректными.

# 6. Склад

## `StockBalance`

Это не «форма для ручного изменения количества».

В списке показывать:

```
Товар
Остаток
Последний приход
Последний расход
Минимальный уровень
Статус остатка
```

Количество в `StockBalance` делать readonly.

Если нужно изменить остаток, пользователь должен создавать:

```
InventoryAdjustment
```

## `InventoryAdjustment`

Это главный безопасный экран корректировки склада.

Поля:

```
Товар
Тип операции: увеличить / уменьшить / установить остаток
Количество
Причина — обязательно
Сотрудник, выполнивший корректировку
Дата и время
```

После создания корректировки:

```
обновляется StockBalance;
создаётся StockMovement;
сохраняется аудит.
```

После сохранения корректировку лучше не редактировать. Если допущена ошибка — создать обратную корректировку, а не переписывать историю.

## `StockMovement`

Только просмотр.

Показывать:

```
Дата
Тип движения
Товар
Количество
Основание
Связанный заказ / контракт / корректировка
Комментарий
```

Не давать пользователю создавать или менять движения вручную, если они рождаются бизнес-логикой.

# 7. Финансы

## `FinancialTransactions`

Это журнал фактов, а не ручная таблица редактирования.

Разрешить:

```
Просмотр
Фильтрацию
Поиск
Экспорт
Переход к источнику операции
```

Ограничить:

```
Прямое создание
Прямое редактирование суммы
Прямое удаление
```

Потому что транзакции создаются из:

```
заказов;
контрактов;
зарплат;
рассрочек;
других операций.
```

Если надо сделать ручной расход/доход, лучше сделать отдельный контролируемый сценарий:

```
«Ручная финансовая операция»
```

с обязательными полями:

```
Тип
Сумма
Дата
Источник / категория
Комментарий
Кто создал
```

## `Finance`

Дневная сводка должна быть readonly.

Её нельзя редактировать руками:

```
доход;
расход;
прибыль;
безнал.
```

Она агрегируется из транзакций.

# 8. Права пользователей

Не используйте одну общую роль «админ» для всех.

Минимально нужны группы:

|Группа|Что может|
|---|---|
|Владелец|Всё, включая финансы, кассу, настройки и исправления|
|Диспетчер|Клиенты, pending-заказы, назначение курьеров и рейсов, просмотр смен|
|Кассир / бухгалтер|Финансы, кассовая сверка, зарплаты, контракты|
|Кладовщик|Склад, инвентаризации, движение товаров|
|Наблюдатель|Только просмотр Dashboard и ограниченного Admin|
|Курьер|Не входит в Django Admin; работает через Telegram/Mini App|

## Пример ограничений

|Действие|Владелец|Диспетчер|Кассир|Кладовщик|
|---|---|---|---|---|
|Создать pending-заказ|✅|✅|❌|❌|
|Изменить доставленный заказ|По спец-сценарию|❌|❌|❌|
|Закрыть смену|✅|✅|❌|❌|
|Сверить кассу|✅|❌/просмотр|✅|❌|
|Инвентаризация|✅|просмотр|❌|✅|
|Смотреть финансы|✅|ограниченно|✅|❌|
|Редактировать товар|✅|❌|❌|✅/ограниченно|

# 9. Что добавить для удобства

## Ссылки между сущностями

Везде сделать быстрые переходы:

```
Заказ → клиент
Заказ → рейс
Заказ → смена
Заказ → курьер
Смена → Dashboard-отчёт
Рейс → заказы рейса
Кассовая сверка → смена
Движение склада → заказ или корректировка
Финансовая транзакция → заказ / контракт / зарплата
```

Это сильнее улучшает работу Admin, чем добавление десятков полей в одну таблицу.

## Сохранённые фильтры

Для диспетчера полезны быстрые ссылки:

```
Заказы без рейса
Заказы в ожидании
Заказы на сегодня
Закрытые смены без сверки кассы
Смены с расхождением
Критические остатки
```

Это можно сделать через:

- кастомные admin views;
- ссылки в верхнем меню;
- стандартные фильтры с query-параметрами;
- отдельный компактный Dashboard.

## Экспорт

Для бухгалтерии и владельца добавить экспорт в CSV/Excel:

```
Заказы за период
Закрытые смены
Кассовые расхождения
Продажи по товарам
Складские движения
Финансовые операции
```

Сначала достаточно CSV/XLSX для выбранного фильтра. Не нужно строить сложный генератор отчётов до появления реальной потребности.

# ТЗ для AI-агента: улучшение Django Admin

```
Нужно провести аудит и улучшить Django Admin в проекте WERP / Osnova 2.0.

Цель:
Django Admin должен стать безопасным и удобным рабочим интерфейсом
для владельца, диспетчера, кассира и кладовщика.

Dashboard остаётся экраном аналитики и контроля.
Django Admin используется для создания, настройки, исправления и аудита данных.

Перед изменениями обязательно изучить актуальные:
- models.py;
- signals.py;
- admin.py;
- формы создания заказа;
- Dashboard;
- API;
- миграции;
- текущие группы и разрешения Django;
- точки, где создаются финансовые и складские движения.

Особенно проверить, какие поля автоматически влияют на:
- StockBalance;
- StockMovement;
- FinancialTransactions;
- Finance;
- cash_total / card_total смены;
- OrderItem.price;
- статистику Dashboard.

После аудита сначала выдать отчёт:
1. Какие модели являются справочниками.
2. Какие модели являются операционными.
```
