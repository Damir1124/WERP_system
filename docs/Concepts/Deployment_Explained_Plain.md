# WERP / Osnova 2.0 — как работает проект и деплой (объяснение простыми словами)

> Этот файл написан для тех, кто не знаком с DevOps-терминами. Здесь объясняется,
> **как технически устроен проект**, **по какой схеме он работает в интернете** и
> **на что способен по производительности**. Точные цифры взяты из конфигов проекта.

---

## 0. Главная идея: «дом с несколькими комнатами»

Представь, что проект — это **многоквартирный дом**. Каждый сервис (см. ниже) —
это отдельная «квартира», которая выполняет свою работу. Они живут **в одном доме**
(на одном сервере), но у каждой своя задача. Если одна «квартира» упадёт — остальные
продолжат работать.

Наш «дом» собирается **Docker Compose** — это программа, которая по одному файлу
`docker-compose.yml` знает, какие «квартиры» строить и как им общаться между собой.

---

## 1. Схема: какие «комнаты» (сервисы) есть и кто что делает

| Сервис (комната) | Его работа | Внутренний адрес |
|---|---|---|
| **db** | Хранит **все данные**: клиенты, заказы, деньги, склад (PostgreSQL) | порт 5432 |
| **redis** | Быстрый «черновик» для временных данных: кэш, очереди задач, WebSocket, состояния бота | порт 6379 |
| **web** | Главный сервер, обслуживает **обычные запросы** (сайт, админка, API) через Gunicorn | порт 8000 |
| **web-asgi** | Специальный сервер для **живых обновлений в реальном времени** (Dashboard) через Uvicorn | порт 8001 |
| **celery-worker** | Исполнитель **фоновых задач** (пересчёт денег, напоминания) | — |
| **celery-beat** | «Будильник» — запускает фоновые задачи **по расписанию** | — |
| **bot** | **Telegram-бот** (aiogram) — общается с пользователями | порт 8001 |
| **nginx** | «Входная дверь» — принимает всё, что приходит из интернета, и раздаёт по комнатам | порты 80/443 |

**Логика:** nginx — единственный, кто «виден» из интернета. Внутри дома сервисы
общаются по именам (`web`, `redis`, `bot`...), а не по IP.

## 2. Почему сервисов несколько? (что даёт такая схема)

Раньше всё крутил один процесс `manage.py runserver`. Это удобно для разработки,
но плохо для продакшена:

| Проблема одного процесса | Решение в нашей схеме |
|---|---|
| Один упал — всё упало | 8 отдельных контейнеров, каждый живёт сам |
| Нет HTTPS (безопасного шифрования) | nginx терминирует SSL |
| Статику отдаёт медленно через Python | nginx отдаёт файлы напрямую, мгновенно |
| Нет фоновых задач | celery-worker |
| Нет расписания | celery-beat |
| Нет очередей | redis |
| Один запрос = одно «окно» | Gunicorn/Uvicorn с несколькими работниками |

## 3. Путь запроса (что происходит, когда курьер нажимает кнопку)

Возьмём пример: **курьер подтверждает доставку** в Telegram.

```
1. Telegram ➜ https://werp.uz/api/bot/orders/... (по HTTPS)
2. nginx  принимает запрос, расшифровывает SSL
3. nginx видит /api/ ➜ передаёт Gunicorn (web, порт 8000)
4. Django обрабатывает: списывает товар со склада, проводит деньги
5. Django отвечает курьеру: «Доставлено ✅» (быстро!)
6. Django ставит «фоновую задачу» в redis
7. celery-worker забирает задачу ➜ отправляет клиенту уведомление
8. Клиент видит: «Ваш заказ доставлен 🎉»
```

Главное: курьеру отвечают сразу (шаг 5), а тяжёлая работа (уведомление клиенту)
делается в фоне — так система не тормозит.

**Живой Dashboard** работает иначе: браузер открывает постоянный канал (WebSocket)
через `web-asgi`. Nginx видит `/ws/` ➜ передаёт этот канал Uvicorn, и данные на
экране обновляются сами, без перезагрузки страницы.

## 4. Мощностные способности (что умеет и насколько силён)

### 4.1 Сколько запросов держит
- **web (Gunicorn): 3 работника** — одновременно обрабатывает до 3 «тяжёлых»
  запросов; лёгкие — тысячи в секунду.
- **web-asgi (Uvicorn): 2 работника** — для живых WebSocket-каналов.
- **nginx отдаёт статику напрямую** — файлы (картинки, собранные приложения)
  раздаются практически без нагрузки на Python.

### 4.2 Фоновые задачи (Celery beat — автоматическое расписание)
| Когда | Что делает |
|---|---|
| Каждый день в 09:00 | Напоминания клиентам о взносах по рассрочкам |
| Каждый день в 00:30 | Сброс просроченных балансов зарплат |
| 1-го числа месяца в 08:00 | Автоматическое начисление зарплат |
| Каждый день в 00:05 | Пересчёт финансовой сводки за вчера |

### 4.3 Функциональные модули (что умеет система)
- **Клиенты** — CRM: карточки, телефоны, адреса, геопозиция, telegram ID.
- **Товары** — каталог питьевой воды и тары.
- **Сотрудники** — курьеры, упаковщики, операторы, владельцы.
- **Склад** — остатки, движения, автопарк машин, инвентаризация, генерация
  путевых листов (.docx).
- **Логистика** — смены → рейсы → заказы (основа логики доставки).
- **Финансы (accounting)** — контракты, рассрочки, зарплаты, дневная сводка.
- **Dashboard** — живая панель управления с WebSocket-обновлением.
- **Telegram-бот + Mini Apps** — отдельные интерфейсы для курьера, клиента,
  оператора, владельца (открываются прямо в Telegram).

## 5. Как это поднять (для понимания, без команд)

1. На сервере ставится **Docker**.
2. Копируется проект (`git clone`).
3. Создаётся файл `.env` с настоящими секретами (из шаблона `.env.example`).
4. Выполняется `docker compose up -d --build` — Docker сам собирает все 8 «комнат».
5. Применяются миграции (Django создаёт таблицы в БД), собирается статика,
   создаётся администратор.
6. Получается **SSL-сертификат** (Let's Encrypt) — чтобы Telegram открывал Mini App.
7. Система работает: nginx слушает 80/443, всё остальное внутри.

Дальше обычные обновления делаются одной командой `bash deploy.sh` (или вручную
по инструкции — она в файле деплой-документа).
